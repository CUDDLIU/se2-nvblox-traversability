# Official FIRST implementation audit

Source: NOS `/opt/robot/share/planner`, ELF build ID `c99ebf84f89e85be231a2b63da1beaeb9d941c1d`. Exact files and hashes: `manifest.json`. Binary and tables are local vendor assets, excluded from Git; no license or source availability is inferred.

Historical reimplementation audit (superseded as the default by the original-binary deployment below). Verified from assets and AArch64 disassembly:

- 4,641 primitives, ten samples at 0.1 s, one second horizon. Samples match forward Euler integration of stored body velocity, not an analytic arc. Test checks every sample (20 μm tolerance for text rounding).
- Hard collisions: `updatePathPenalty` 0xb9658–0xb966c increments for every table occurrence. Repeated IDs within a row matter.
- Soft flags: 0xb9688–0xb9700 sets each path flag to one. It does not sum hits or divide by sample count. The historical Python planner differs here.
- Score: endpoint Euclidean distance, wrapped heading error towards the local goal, absolute lateral velocity, three binary proximity flags, and a +1 penalty when the goal is in front and native vx ≤ 0.05 (`0xd4288`). See 0xb9f90–0xba0cc.
- YAML parameter offsets 272/280/288 are goal/yaw/lateral. Offsets 296/304/312 are weight_ob1/2/3 (`loadParameters` 0x974cc–0x975e0). The binary multiplies soft arrays at offsets 264/288/312 by parameters 312/304/296 respectively: innermost soft table is weighted 1.0, middle .8, outer .6. This is opposite to the table labels' apparent numeric order.
- Loader: PathData offsets 72/96/120/144 correspond to base, _4, _5, _6. `readCorrespondences` 0xc1a7c–0xc1c78.
- `PlannerLoop` chooses separate `runDWA` / `runLine`. `runDWA` checks cancellation, initializes zero velocity, snapshots grid, evaluates penalties/candidates, validates selected path, computes command and publishes. Candidate rejection can retry up to 100 times.

- `CmdCalculate` 0xbd830–0xbd920: outside 0.5 m it copies native selected velocity; inside, until 0.1 m, it commands goal error with the native proportional/minimum-component loop (start multiplier 0.5, increment 0.05; x/y threshold 0.25).
- `CmdCalculate` 0xbdd74–0xbe064: inside position tolerance, zero linear velocity, wrap yaw error, accept within 0.1 rad; otherwise use signed 0.7 rad/s for smaller errors or 1.5 × error, then validate rotation. Project gait caps limit the command before its actual swept collision check.
- `cmdVelLimit` 0xba9a8–0xbad64 clamps maximum x/y/yaw and processes cancellation/status. No per-axis minimum candidate filter was found here. Extra minimum-component candidate filters were removed to retain native gentle curves.

Project extension after the audited score: an optional previous-command continuity cost, capped at 0.08, is added during native candidate ranking. It uses only a fresh valid same-generation command and never changes an output velocity after collision validation. The `score()` kernel above remains unchanged; the augmented ranking is deliberately not claimed to reproduce the official binary.

Not yet established as behavior-equivalent:

- Full outer `CmdCalculate` status handling, `LinePlanner` turn/approach/stop transitions, acceleration handling and all numerical planner status meanings.
- Full original-binary input/output comparison. The binary uses DrDDS and is not a ROS executable; it has not been executed against synthetic input.
- New stair gait logic and 3D terrain adaptation are project extensions, not recovered official source.

The independent ROS node currently implements DWA selection, the audited terminal controller and fail-closed input/cancel handling. It must not be described as a complete recovered official state machine. Hardware output is opt-in with `--execute`; supervised flat-route trials are documented separately. These trials do not establish complete state-machine equivalence or staircase acceptance.

## 2026-10-13: live NOS identity, window geometry and local obstacle pipeline

Read-only SSH verified the running NOS files against the captured `localPlanner` and both YAML hashes above. Processes 2877/2878 were `localPlanner` / `pcl_pass_grid`; the official startup script runs both with `chrt 50 taskset -c 6,7`. No service was stopped, restarted, attached with a debugger, or given a goal. Newly captured `pcl_pass_grid` SHA-256: `a51736b0b86bb6a202a915f6bb7c22b9ddf50162efc7bab9823f163ddfee68a9`. Machine-readable evidence: `nos_20261013/manifest.json`; local raw export `/tmp/nos_planner_audit_20261013.tgz`. Its AArch64 disassembly is saved locally as `pcl-pass-grid-disassembly.txt` (excluded from Git).

### Three distinct sizes

- Desktop backup PGTT elevation map: 4.20 × 2.20 m, tracking point 1 m forward, 5 cm cells. This is a terrain observation map, not evidence that the FIRST correspondence table has these dimensions. The backup references an absent `m20_v2_nx` FIRST configuration.
- NOS `pcl_pass_grid.yaml`: X/Y each −4 to +4 m, an 8 × 8 m point-cloud input box; Z −.30 to +.60 m in the input/body coordinate convention.
- NOS `localplanner.yaml`: `grid_voxel_num_x=90`, `grid_voxel_num_y=80`, `grid_voxel_size=.05`, offsets −1.475/−1.975. The correspondence lookup spans **4.5 × 4.0 m**, with X in [−1.475,3.025), Y in [−1.975,2.025). `loadParameters` 0x9790c–0x979f4 reads these values. `updatePathPenalty` 0xb9520–0xb9594 converts occupied-cell centers to table indices, rejects out-of-range indices, and computes `ix*80+iy`. It does not stretch an arbitrary rectangular cloud into this table.

`nos_20261013/window_audit.py` reproduces the template-footprint calculation. Across all native templates using official .84 × .50 m body dimensions, sample footprint corners reach Y ±1.53687 m. With this project's current speed caps and padded footprint, 80 templates still extend outside Y ±1.1 m, reaching ±1.36520 m. A 4.2 × 2.2 m body-aligned crop therefore misses some admissible curved trajectories. A world-axis-aligned 2.2 m width is even less suitable: after a 90° turn, the long forward sweep crosses the narrow world axis. This is a counterexample, not a claim that ten samples certify continuous clearance. Keep the deployed 5 × 5 m window pending any deliberate frame/coverage redesign. A table-aligned implementation must use the official offset and body-frame rotation, not just matching meter dimensions.

### Verified obstacle processing

1. `pcl_pass_grid::main` 0xc6f0c reads its YAML; at 0xc7330/0xc7380 it constructs `/NAV_POINTS` output and `/LIDAR/POINTS` input. `pointCloudCallback` starts at 0xc678c.
2. Actual callback order is X/Y/Z PassThrough (through 0xc6a14), 1 cm VoxelGrid (0xc6a1c–0xc6aa0), negative CropBox removing the body region (0xc6aac–0xc6bcc), then radius outlier filtering (0xc6bd8–0xc6c50). YAML specifies the inner box X ±.45, Y ±.25, Z [−.30,.60], radius .10 m, minimum-neighbor setting 4. The callback assigns `base_link` at 0xc6d24. Follow-up execution disproved the initial timestamp-preservation interpretation: 0xc6c78–0xc6d08 uses integer `sec()` twice and computes `nanosec=(sec-floor(sec))*1e9`, always zero; there is no coordinate-transform call in this callback. These numbers are captured configuration values, not an independent calibration of the incoming coordinate frame.
3. `LocalPlannerNode::laserCloudHandler` 0x94560 receives processed points. It computes current cloud extrema at 0x94a48–0x94a88, constructs a fresh sparse 3D grid at 0x94da4 onward, floors point coordinates by the configured .05 m grid size, counts returns per voxel, and writes occupancy 100 only when count is at least `grid_occu_num_` (configured 2; 0x94fc0–0x9505c). At 0x95124–0x9517c it replaces the shared grid. This audited nonempty-cloud path rebuilds from the current scan; it is not the project's persistent world-frame occupied/free/unknown ray-clearing grid. Missing or invalid input has separate continuity checks; this finding does not authorize clearing obstacles on sensor silence.
4. In DWA mode, `updatePathPenalty` maps occupied grid centers through the four correspondence tables, then `pathScoreAndSelect` ranks native trajectories. `judgePath` 0xb9b08 checks the ten nominal sample poses against obstacle XY using a rotated rectangle with configured robot length/width (0xb9c60–0xb9cb0); `block_number=1` makes any counted hit fail at 0xb9cfc–0xb9d10. It is not this project's 2.5 cm interpolated padded sweep with terrain-relative height and braking coverage. Rejected selected candidates are retried, with the existing audited retry bound.
5. `PlannerLoop` dispatches `runDWA` at 0x96524 or `runLine` at 0x9666c. Captured YAML defaults to `directLine_mode: true`, but the parameter service can change that at runtime; the active mode for any physical trial cannot be inferred from YAML alone.
6. The direct-line branch uses `judgeDirect` / `detectObstacleInROI` (0xc60e0 / 0xc5aa0). Its forward rectangle starts at half body length, ends at half body length plus `min(goal_distance, stop_distance)`, and spans ±half body width (0xc6260–0xc6314); backward mode flips the X interval. This is a separate obstacle-stop control path, not selection among the 4,641 DWA primitives.
7. On obstruction, `LinePlanner::handleApproach` zeroes translation, compares heading error, calls `judgeRotate` (0xc6bf0), and only on success emits a dedicated signed yaw command from config offset 184 (0xc6c18, 0xc6f7c). The ELF initializes that field to .35 rad/s. The inspected branch's error threshold is config offset 192, converted from degrees at 0xc6b34–0xc6b60; the ELF default is **5°**, although the YAML text says `adjust_yaw_min_: 1`. The inspected YAML loader and `paramHandler` do not assign these two fields, so the YAML line alone is not evidence of a 1° effective threshold. This is static binary analysis, not a live-memory read. A failed rotation check stops motion (0xc6e44–0xc6e60). The broader state machine remains only partially audited.

### Implications for the current corner failure

The native template library alone does not reproduce official obstacle behavior. Current differences include low-point acceptance, persistent world-frame evidence, terrain-relative 10 cm height classification, padded/interpolated swept collision checks, path-heading ranking and separate reverse recovery. The latest collision voxel was supported by eight new observations, at raw Z approximately −.3536 to −.4186 m. If those coordinates were supplied unchanged to the captured NOS preprocessing configuration, its −.30 m cutoff would reject them. **This is a conditional offline comparison**, not proof that NOS receives the same calibrated coordinates or that the points are false obstacles. Raising the current cutoff would also remove real low obstacles and is not part of this audit.

The observed current body/route heading error was about 6°, while the positional target required rightward correction and near-body collision repeatedly rejected forward and reverse sweeps. The official separate stopped-yaw branch is relevant to weak-turn symptoms, but is gated by its own rotation clearance check and belongs to direct-line mode. No official .35 rad/s override, single-frame forgetting, body crop or height cutoff has been transplanted into the deployed controller on the strength of static analysis alone. Current map remains 5 × 5 m. Original-binary input/output equivalence and physical corner clearance remain unverified.


## 2026-10-13: original-binary deployment (supersedes the custom default)

The default launcher now runs hash-identical `localPlanner` and `pcl_pass_grid`, with their NOS shared libraries, inside rootless bubblewrap namespaces on Jetson. It uses the original tables and filtering YAML. A session copy sets `local_try=false`; `/set_service` sets `directLine_mode=false` with the remaining service fields copied from captured defaults. This selects the official external-local-goal autonomous branch. ASA/global localization remain project code; the ROS adapter selects its path lookahead and does not generate local velocity candidates or collision decisions.

Runtime checks resolved by comparing binary instructions with tests:

- `pcl_pass_grid` and localPlanner point-cloud subscriptions pass `use_shm=true` (0xc73c4 / 0x8dd68). Matching only the topic name was insufficient for full-size cloud transport. The bridge now uses the same shared-memory channels inside its isolated `/dev/shm`.
- `DwaPlanner::updateLocalGoal` 0xb8fb0–0xb900c rejects repeated stamp intervals outside [0.05,0.20] s; passing 30 Hz local goals accumulates a failure count. The adapter supplies 10 Hz.
- The filter drops nanoseconds as described above. The bridge serializes cloud input with exactly one in flight; only the ROS result's stamp is restored from that corresponding input. It never refreshes stale data with wall time. Native filter/planner geometry and native DDS messages are unmodified.
- Planner loading was measured at 5666 ms, followed by an explicit two-second initialization. The adapter waits for service readiness and goal acknowledgement.
- `/NAV_CMD` was measured at 10 Hz with 1.5 m/s straight commands. The actual corner simulation used lateral speed up to the native float32 .6 m/s and yaw up to .8 rad/s. The sender's opt-in official profile preserves these commands; the old .4 m/s lateral limit remains restricted to the legacy profile.

The final 90° L-corridor simulation reached (2.42890,2.93043,1.61131) for target (2.4,3.0,pi/2), about 7.53 cm position error and 2.32° yaw error. No .84×.50 m body rectangle overlapped sampled corridor walls. Cloud loss, cancellation/replacement and localization loss produced zero output in their asserted windows; recovery produced fresh commands. Original binary and adapted ROS logs plus summarized results are retained under `evidence/native_20261013/`; complete test runs remain on Jetson under `/tmp/native_release_corner`, `/tmp/native_release_gates`, `/tmp/native_captured2`. These isolated tests do not establish physical corner or stair acceptance.

The real captured-cloud replay reported 117 normal outputs, 3 freshness holds and 51 initialization samples. Native filtering/transport median was 48.34 ms, p90 51.53 ms, p99 67.38 ms; processed scan-end age median was .175 s. Those three holds remain a measured limitation, not a physical trial result. The default still fails closed at .35 s rather than hiding the gaps. Native gait is left at the current robot setting; the removed custom terrain-based gait switcher is not silently retained.

## NOS stair-related chain inspection, 2026-10-14

Read-only inspection found running `passable_area` and `accumulate_cloud`, but the NOS local-planner launch script currently selects `pcl_pass_grid`; its `pcl_remove` alternative for `/impassable_area` is commented out. The alternative binary contains `/impassable_area` input and `/NAV_POINTS` output. The passability configuration is 8×8 m at 5 cm and includes separate slope/roughness/step costs. These configured thresholds are not physical climbing guarantees.

The separate `handler` accepts `/HANDLE_STEER` x/y/yaw commands and `/cloud_nav`. Disassembly confirms `SetOoaParamCallback` reads `StairOA` at 0x9bfb0, and `CheckStairOaEnabledState` sends the desired boolean as command 0/1 through `/HEIGHT_MAP_STAIR_OA_ENABLE` (0x9c250–0x9c284). This proves a stair obstacle-avoidance interface; it does **not** prove automatic stair gait selection or autonomous ascent. The service implementation and its classification semantics have not been recovered. The original local-planner integration alone therefore cannot be described as complete NOS stair support. Configuration, function disassembly and hashes are retained in `nos_stairs_20261014/`.
